# IBlueConnect V2 — research findings and proposed direction

Date: 2026-10-01.

Status: research and planning. The user requested that these findings form the planning document for the next version of IBlueConnect. No V2 messaging, file-transfer, notification-mirroring, or USB features have been implemented or verified on the user's phone. Repository claims below are upstream reports, not IBlueConnect acceptance results.

## 1. Product direction

Expand IBlueConnect from a cellular-call companion into a local iPhone companion with file transfer, individual text conversations, and optional access to other supported phone data.

The recommended sequence is:

1. LocalSend-compatible file transfer.
2. Individual Bluetooth text messages, subject to a phone compatibility check.
3. Optional notification mirroring and clipboard/link sharing.
4. Optional USB access to eligible documents, device information, and backups.

Actual AirDrop interoperability and group-message sending remain experimental research topics. Full Apple Messages synchronization and unrestricted phone access are not established capabilities.

This document records a proposed V2 scope. It does not replace the current calling behavior or authorize system changes. Existing decisions in [AGENTS.md](AGENTS.md), [HANDOFF.md](HANDOFF.md), [IBlueConnect_Spec.md](IBlueConnect_Spec.md), and [Feasibility.md](Feasibility.md) remain authoritative; their latest updates supersede historical instructions.

## 3. Bluetooth messaging

### Integration path

BlueZ exposes `org.bluez.obex.MessageAccess1`, including message listing and `PushMessage` for sending a bMessage. The existing daemon already uses BlueZ OBEX for PBAP contacts/history, and already has Rust D-Bus and SQLite dependencies. A focused MAP integration could reuse those facilities.

Source: [BlueZ MessageAccess API](https://github.com/bluez/bluez/blob/master/doc/org.bluez.obex.MessageAccess.rst).

An initial Messages view could receive individual texts, compose messages, reply, resolve contacts, and retain a bounded local history of messages actually observed or sent by IBlueConnect. Bluetooth messaging does not require a custom iPhone companion app in the researched implementations. Phone-side message-notification permission is required; whether the existing pairing offers it is unverified.

### Limits and conflicting findings

- Local history is not a downloaded copy of the complete Messages archive. Do not invent missing conversations or imply complete synchronization.
- Messages sent directly on the phone may not appear in the bridge's history.
- Rich message features and attachments are absent from the researched Bluetooth path.
- The phone chooses SMS/iMessage routing; the Linux client cannot assume or force blue-bubble delivery.
- A successful MAP transfer means the phone accepted the message, not proof that the recipient received it. An ambiguous timeout must not trigger an automatic resend.
- Group sending is unresolved. Tincan reports delivery only to the first recipient; Tether and BlueFerry describe conditional support using notification correlation and inferred member lists. Group replies should stay unavailable until recipients can be identified and behavior is verified.
- RCS findings vary, including contradictory statements within Tincan's limitations document. Keep RCS support explicitly unverified.

Sources: [iphonebridge limitations](https://github.com/gabrielmeir53/iphonebridge#-limitations), [Tincan limitations](https://github.com/quad341/tincan/blob/main/docs/LIMITATIONS.md), [Tether protocol findings](https://github.com/zackb/tether/blob/main/docs/BLUETOOTH.md), [BlueFerry](https://github.com/erikwb/blueferry).

Microsoft also documents restricted history, no image/GIF support, and no group replies in Phone Link for iPhone. This corroborates the limited Bluetooth experience; it does not prove that every experimental Linux workaround is impossible.

Source: [Microsoft Phone Link messaging documentation](https://support.microsoft.com/en-us/windows/apps/phonelink/send-and-receive-text-messages-from-your-pc).

For a richer iMessage experience, [BlueBubbles](https://github.com/BlueBubblesApp/bluebubbles-server) is a separate Mac-based relay option. It would introduce another computer and account-based infrastructure, so it is outside the recommended direct-phone V2 baseline.

## 4. File transfer and AirDrop alternatives

### Recommended: LocalSend compatibility

LocalSend supports iOS and Linux and publishes a local-network transfer protocol with discovery, transfer preparation, upload/download, and cancellation. It does not require an external server. IBlueConnect could provide the laptop interface while the phone uses LocalSend.

The current upstream tree already includes a Rust core and CLI. Review and reuse the needed transport facilities before considering a protocol rewrite. The presence of Rust source does not establish a stable embedding API or compatibility with the current iPhone release; both require checking.

Use the same reachable local network for the initial scope. Receiver availability and iPhone app/background behavior need verification. This is an AirDrop-like workflow, not a claim that the laptop appears in Apple's built-in AirDrop picker.

Sources: [LocalSend repository](https://github.com/localsend/localsend), [protocol](https://github.com/localsend/protocol), [Rust core manifest](https://github.com/localsend/localsend/blob/main/packages/core/Cargo.toml), [Rust CLI manifest](https://github.com/localsend/localsend/blob/main/cli/Cargo.toml).

### Other useful paths

| Option | Useful role | Tradeoff |
|---|---|---|
| [PairDrop](https://github.com/schlagmichdoch/PairDrop) | Transfer through a modern browser; self-hosting is supported | Uses WebRTC and signaling; hosted/internet operation can involve STUN/TURN infrastructure |
| [Tether](https://github.com/zackb/tether) | Existing file/clipboard companion and phone share-extension reference | Separate phone app and protocol; desktop clipboard integration targets particular Wayland capabilities |
| [KDE Connect iOS](https://github.com/KDE/kdeconnect-ios) | Existing LAN companion worth evaluating | Official documentation identifies foreground/background restrictions; its companion cannot read other apps' notifications |
| Native Files “Connect to Server” | Access a laptop shared folder from the phone without creating a custom phone app | Requires configuring a file server; this is folder access, not an AirDrop picker |

Source for the native option: [Apple's file-server workflow](https://support.apple.com/en-jo/guide/iphone/iphe9aff429a/ios). On Linux, an SMB share is an option to evaluate rather than implement a new file-server protocol.

### Experimental: actual AirDrop

[OpenDrop](https://github.com/seemoo-lab/opendrop) implements AirDrop in Python. Linux requires AWDL support such as [OWL](https://github.com/seemoo-lab/owl), a C implementation needing active monitor mode and frame injection. OpenDrop documents incomplete discovery/authentication and automatic acceptance in its receiver implementation.

Keep this separate from the ordinary transfer feature. Do not adopt those acceptance semantics or assume compatibility with current iOS. A Rust translation cannot remove radio/driver requirements or Apple protocol changes.

**2026-10-17 research (decision deferred by the user).** [omdrop-owl](https://github.com/t4t5/omdrop-owl) (GPL-3.0/GPL-2.0/ISC) packages patched OWL with the MIT [omdrop CLI](https://github.com/netmojo-systems/omdrop-plugin) (`status --json`, `peers --json`, `send`, `on`/`off`, `doctor --json`). This laptop's Intel AX211 (`8086:51f0`, `iwlwifi`, Ubuntu 26.04, kernel 7.0) is listed as working only in **exclusive** mode: Wi-Fi disconnects while visible. Installation needs root (polkit policy, NetworkManager unmanaged rules, udev `.link`). AirDrop uses Bluetooth LE only for discovery; files travel over AWDL Wi-Fi, and iOS has no Bluetooth file transfer. Options offered: (A) own Rust AirDrop including AWDL — months, still needs one-time root setup and exclusive mode; (B) own Rust discovery/protocol/UI with OWL as the AWDL layer — weeks; (C) Rust BLE discovery plus a LocalSend-compatible transfer — about 1–2 weeks, no Wi-Fi drop, not in Apple's share sheet. Recommended C now, B later. Credit OWL, OpenDrop and omdrop-owl in any port. Nothing was installed.

### FaceTime Audio (2026-10-17 research, decision deferred)

HFP carries only cellular calls. [rustpush](https://github.com/OpenBubbles/rustpush) (used by [OpenBubbles](https://github.com/OpenBubbles/openbubbles-app)) implements FaceTime signaling (`ring`, `join`, `decline`, `leave`) and SRTP/QuickRelay media with AAC audio, making the laptop its own FaceTime device. Constraints: Apple ID + 2FA on the laptop; Apple device validation needs a Mac or OpenBubbles' paid hosted relay (the user has no Mac; the phone's iOS 27 rules out the iPhone route); rustpush is SSPL and its `LICENSE.exceptions` covers only OpenBubbles; possible Apple ID flagging; no Linux client has working FaceTime audio yet. OpenBubbles publishes a Linux x86_64 build (v1.15.0+205), untested here. facetime.apple.com links do not support Firefox. Options: launch OpenBubbles from a button (no license mixing), a separate SSPL helper over D-Bus, or request an exception. A GPL-3.0 project license was proposed; the user is considering it. Nothing was installed.

## 5. Access beyond files

### Notifications

ANCS exposes notification arrival, modification, removal, attributes, and limited predefined actions over BLE/GATT. It is not a general app-data API or a universal text-reply interface. Notification bodies depend on the phone's preview policy.

Adapter, bond, and BlueZ requirements differ between projects. Treat notifications as a separate capability from MAP/PBAP; working contacts or messages do not prove ANCS works. Some setup paths require Bluetooth changes or re-pairing, which need a later user decision.

Source: [Apple ANCS specification](https://developer.apple.com/library/archive/documentation/CoreBluetooth/Reference/AppleNotificationCenterServiceSpecification/Specification/Specification.html).

### Photos, calendars, reminders, and clipboard

A custom phone companion could request access to supported data through Apple's APIs and share approved data with the laptop. This is an architectural inference, not an existing IBlueConnect feature. Photos and calendar/reminder access require their respective permissions; clipboard sharing also needs a workable foreground or explicit-sharing flow.

Sources: [PhotoKit](https://developer.apple.com/documentation/Photos/PHPhotoLibrary), [EventKit](https://developer.apple.com/documentation/eventkit/accessing-the-event-store), [KDE Connect's background limitations](https://github.com/KDE/kdeconnect-ios#known-behavior-and-problems).

### USB and device services

[idevice](https://github.com/jkcoxson/idevice) is an MIT-licensed Rust library exposing services including AFC, House Arrest, diagnostics, and backups. It describes itself as under development, so exact service and iOS compatibility need validation.

[libimobiledevice](https://github.com/libimobiledevice/libimobiledevice) is an established C library exposing eligible file-sharing documents, backups, device information, and other services, with network support for configured Wi-Fi-sync devices. Reuse through bindings or existing tools is also an option.

These services require a separate trusted connection. Eligible app documents are not unrestricted access to every app container. Some developer services require additional phone setup; screenshots or diagnostics do not establish everyday screen mirroring or remote control.

### Permission boundaries

There is no normal “allow everything” permission. Third-party iPhone apps remain sandboxed and access other data through services explicitly provided by iOS. User consent does not create an API for private databases, passwords, or arbitrary control of other apps.

Source: [Apple platform security — runtime and sandboxing](https://support.apple.com/en-au/guide/security/sec15bfe098e/web).

## 7. Rust and architecture recommendation

Keep the existing Rust daemon and C/GTK/libadwaita UI. Add only integrations justified by verified capabilities.

- Reuse the existing D-Bus, contacts, and SQLite facilities for messaging where appropriate.
- Evaluate LocalSend's Rust core before writing another transfer stack.
- Evaluate idevice or bindings to libimobiledevice for the optional USB path.
- Port small needed protocol/state logic only when direct reuse is unsuitable. Avoid importing an entire second desktop application or copying its installers.
- Keep calling readiness, messaging readiness, network-transfer availability, and USB trust separate. A working call link must not imply every V2 feature is available.
- Start optional work only when enabled or needed, and measure all added processes and dependencies.

Rust can reduce interpreter overhead and improve memory safety. It does not automatically improve Bluetooth/network throughput, remove iOS restrictions, or make an existing C library faster. Measure memory, CPU, latency, and transfer throughput before claiming optimization.

## 8. Existing behavior to preserve

- Keep the permanent, user-approved oFono HFP backend, its rollback, and the verified call-only RNNoise route.
- Never initiate the laptop-to-iPhone Bluetooth link. The user connects manually; any future additional bearer requirement needs an explicit decision if it conflicts with that policy.
- Keep the quiet background daemon, app-icon main-window opening, floating incoming/active controller, Ignore semantics, and no auto-answer.
- Synced missed calls remain silent. Researching general notifications does not change the existing call-alert policy.
- No Bluetooth/audio service changes or risky phone operations without user approval. A daemon restart requires a fresh privately parsed idle Snapshot.
- New access should have separate opt-ins and truthful unavailable states. Denied file/message/notification access must not block calling.
- Never print message bodies, phone numbers, contact names, call times, device addresses, or other private phone data in diagnostics. Protect caches and temporary message files.

## 9. Verification before implementation claims

| Stage | Smallest useful evidence |
|---|---|
| Compatibility research | Exact phone/iOS build, available message permission and MAP service, adapter/BlueZ capabilities; private data stays private |
| Files | Interoperate with the phone app in both directions; verify bytes, accept/decline, cancellation, connection loss, and safe handling of untrusted filenames |
| Messaging | Test parsers/state offline first; then user-operated individual sends/receives, non-ASCII text, permission denial, disconnect, and ambiguous send results |
| Notification mirroring | Separate opt-in; verify preview/lock behavior, duplicates, reconnect, hardware support, and only supported actions |
| Clipboard/companion | Verify both directions and actual iPhone foreground/background behavior |
| USB | Verify trust denial, unplug/reconnect, eligible document access, and each required service on the exact phone |
| Calling regression | Preserve user-operated call/audio behavior while optional features are enabled; do not place or answer test calls automatically |
| Delivery | Check supported Ubuntu builds, dependency/license notices, Undo, and measured total app resources |

No new phone probe, message send, transfer, pairing, installation, or Bluetooth/audio change occurred for the research recorded here. The next V2 decision is which proposed capability to validate first; these findings do not authorize implementing every listed feature.
